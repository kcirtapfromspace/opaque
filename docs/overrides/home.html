Built for platform and security teams whose developers already run AI coding agents. The agent asks for work. Opaque checks policy, gets human approval out of band, executes against your secrets provider, and returns a sanitized response. Every operation leaves a tamper-evident audit trail.

Who runs Opaque

Engineering teams of ten or more whose developers already use AI coding agents. Today those teams either keep sensitive access away from the agent or watch its every move. Opaque is not another secrets manager or agent framework. It decides what may pass between the two you already have, and proves what did.

The security or platform lead

Owns policy and custody. Decides what agents may touch and which operations need a human. Can show an auditor, or a SIEM, what happened and who approved it.

policy · custody · evidence

The developer

Stops watching every action. Hands the agent real work: publish the secret, dispatch the release, run the host check. Approves the exact scope once and reads the receipt.

approve once · read the receipt

The agent

Finishes the task. Claude Code or Codex gets operations, never plaintext. There is nothing in its process worth stealing.

operations, never values

Every operation clears five gates

There is no fast path. An operation either takes this route through the daemon, or it does not happen.

  1. Policy

    Deny by default. Allowlist rules match the operation, the client's verified executable identity, the workspace, and the principal's live roles. Identity constraints fail closed.

  2. Approval

    Out of band and operation-bound: Touch ID, polkit, a paired device, or a FIDO2 key. Each approval is bound to a content hash of exactly what it authorizes.

  3. Execute

    The daemon performs the operation itself, against the provider. Plaintext never enters the agent's process; sandboxed exec runs under bubblewrap, Landlock, and seccomp.

  4. Sanitize

    Responses pass typestate-enforced sanitization, then secret-pattern scrubbing. Returning an unsanitized response is a compile error.

  5. Audit

    Every event lands in an HMAC hash chain in SQLite, with correlation IDs and the approver's identity. One command verifies the chain end to end.

Built for the case where the agent is the adversary

Accidental disclosure is the easy problem. These guarantees are designed to hold when the process asking for secrets is actively trying to take them.

Trust-domain enforcement

Run the daemon under a dedicated service account, or in a separate container, that exclusively owns every key, database, and config. Startup fails closed on any custody violation, and connections from the daemon's own uid are refused. Tamper-evidence becomes tamper-prevention.

[trust_domain] enforce = true

Signature-bound approvals

A pluggable factor registry: local biometric, a paired second device with Ed25519 decision-bound signatures and a fingerprint-confirmation pairing ceremony, FIDO2 hardware keys and passkeys verified daemon-side. The audit chain records who approved, cryptographically.

approver: paired_device ed25519, verified

Tamper-evident audit

Structured events under an HMAC hash chain that survives restarts, with correlation IDs and principal snapshots. Tail truncation is detected through an in-database head anchor, and verification is one command.

$ opaque audit verify

Sandboxed execution

Exec children actually run under bubblewrap with Landlock and seccomp applied. Response sanitization is enforced by the type system: an unsanitized response does not compile.

bwrap + landlock + seccomp

Identity substrate

Humans log in at your IdP over OIDC: PKCE, loopback redirect, owned by the daemon, so an agent driving the CLI cannot complete a login. Agents act on-behalf-of via Ed25519 delegation tokens, roles resolve live at request time, and segregation of duties can require a distinct approver.

sub=hum_9f42 act=agt_claude mode=delegated

Deny-by-default policy

Nothing is allowed until a rule allows it: operations, executables, workspaces, principals, access modes. Presets cover common agent workflows; anything unmatched is denied, and audited.

operation_pattern = "github.*"

Two trust configurations

Where the daemon runs decides what an attacker holding the agent's uid can touch.

Session mode tamper-evident

The default. The daemon runs as your own user, inside your GUI session, and approvals are local: Touch ID on macOS, polkit on Linux. A process sharing your uid could read the chain key and rewrite state. You would detect it after the fact with opaque audit verify.

~/.opaque, LaunchAgent / systemd --user

Trust-domain split tamper-prevention

The daemon runs as a dedicated service account, or in a separate container that shares only the socket with the agent. Custody files are unreadable and unwritable at the agent's uid; in containers they have no path at all. Startup fails closed on any violation. Approvals move to out-of-band factors: a paired device, a FIDO2 key, a passkey.

/etc/opaque, LaunchDaemon / systemd / compose / k8s

Every startup records a trust_domain.posture event in the audit chain, so "was the split enforced at the time?" is answerable from the log itself. The two-mode matrix lives in the deployment guide.

One signature governs the fleet

The guarantees above hold on one machine. These hold across every machine that runs the daemon, without a server anyone has to trust.

Signed policy bundles

Your org signs its policy once; every daemon verifies the signature against its trust anchors before the payload is even parsed. Version rollback is refused from custody: an older bundle, or a different bundle wearing a version already applied, never takes effect. Serve it from any static host: trust comes from the signature, not the channel.

opqb1 · acme v7 · rollback refused

An audit stream your SIEM can verify

Export tails the hash chain itself, so every record arrives carrying its sequence number and chain hash. It is evidence, not a parallel log that can drift. Spool, webhook, or RFC 5424 syslog over TLS, each with its own cursor so one dead collector never stalls the rest.

seq=4182 record_hash=9a2b42bf…

Prove posture before trust

A daemon re-verifies its own custody and audit chain on an interval and signs the result against a caller's nonce. A key verifier can demand that proof before releasing custody material. This is the seam where KMS or SPIFFE/SPIRE plugs in. A tampered daemon cannot quietly collect fresh keys.

$ opaque attest --key <hex>

Team rosters ride in the bundle, so a rule can read teams = ["platform"] and membership resolves daemon-side at request time. The whole model is in the federation guide.

Install

Three binaries: the trusted daemon, the CLI, and the MCP server.

Homebrew (macOS)

brew install kcirtapfromspace/tap/opaque

Shell script (Linux, macOS)

curl -sSfL https://raw.githubusercontent.com/kcirtapfromspace/opaque/main/install.sh | sh

Cargo (from source)

cargo install --git https://github.com/kcirtapfromspace/opaque.git opaque opaqued opaque-mcp

opaqued is the trusted daemon (enclave, policy, approvals, audit); opaque is the CLI; opaque-mcp is the MCP server for Claude Code. Service definitions for launchd, systemd, docker-compose, and Kubernetes ship in the repository's deploy/ directory.

Start with a preset, opaque init --preset github-secrets, then point your agent at the socket.
